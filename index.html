#AgentGames · Proof Gatekeeper teardown

A valid proof is not a valid payment

Six of the seven traps in zkVerify's Proof Gatekeeper produce a proof that verifies perfectly. I built an agent around that fact, and the interesting part was not the cryptography — it was refusing to trust it.

jakadul Event 01 — Proof Gatekeeper 2026 #AgentGames

The trap is the premise

The arena issues a payment request: a recipient, a minimum balance, a transfer cap, an expiry block, and a Groth16 proof that a third party submitted to back the request up. Twenty seconds of reading the rules is enough to notice what the game is really testing. Over 20,000 tasks were issued across eight rounds. Roughly half are clean. The other half are traps, and almost every one of them arrives with a genuine proof attached.

That is the whole lesson compressed into a scoring table. If your agent asks the question "does the proof verify?" it will approve nearly every trap in the set and lose six points each time. The proof is not the decision. The proof is one input to the decision.

Six rejections. Six of them can carry a valid proof. This is not a trick question — it is the standard failure mode of every system that treats verification as authorization.

What the agent actually checks

The order matters, because it decides which reason code you report when a request is wrong in more than one way. Identity first, then freshness, then destination, then value, then replay:

// lib/gatekeeper.js — deterministic, no model in the path
if (!sameHex(proofVk, registeredVk))        return REJECT('VK_SUBSTITUTION');
if (currentBlock > expiryBlock)             return REJECT('EXPIRED_CONDITION');
if (!sameHex(recipient, conditionRecipient)) return REJECT('RECIPIENT_MISMATCH');
if (amount > maxTransfer)                    return REJECT('AMOUNT_OVERFLOW');
if (balance < minimum)                       return REJECT('THRESHOLD_MISMATCH');
if (ledger.has(proofTx))                     return REJECT('PROOF_REUSED');
return APPROVE('VALID_CONDITION');

Three implementation details did more work than the rest of the file combined.

1. Money is never a float

Amounts arrive as decimal strings. parseFloat on a transfer cap is a bug waiting for the right input, and "999.999" versus "1000" is exactly the kind of near-miss a scorer writes into a trap. Everything is parsed to BigInt, and any fractional remainder is treated as unparseable rather than rounded into a decision.

2. The proof ledger has to survive a restart

PROOF_REUSED is ~11% of tasks. An in-memory Set catches replays within one process lifetime and then forgets everything the moment the platform retries after a deploy. The ledger writes to disk with an atomic rename and only records references that were accepted — a proof that was rejected for a substituted VK has not been spent, and refusing it forever would be its own bug.

3. Authentication runs on raw bytes

The task envelope is signed. If you JSON.parse first and verify afterwards, you have already handed unauthenticated input to your parser, and signature checks over re-serialised JSON fail the moment key order or whitespace differs. The handler computes HMAC-SHA256 over the exact request buffer, compares in constant time, and only then deserialises. Responses are signed the same way, over the exact bytes sent.

Fail closed, and mean it. Unknown envelope type, unreadable body, unparsable amount, handler exception — each one returns REJECT. The single worst outcome in this event is approving by default when something unexpected arrives, and it is also the easiest mistake to ship, because the happy path never exercises it.

Evidence, not adjectives

The agent is a Node service behind a TLS tunnel, registered at /agent. The platform's preflight handshake — a signed request that checks your endpoint authenticates and signs correctly before any task is ever delivered — came back clean in 73 ms. Ten for ten, every decision inside a tenth of a second against a sixty-second window. A replay harness in the repo covers the same branches offline, including the two negative cases that matter most: a body signed with the wrong key, and a request with no signature header at all. Both are rejected before the JSON is touched.

Where the proof actually belongs

So far this sounds like the proof is the villain. It is not — it is the part that makes the rest of the system checkable by someone who does not trust me.

The Proof Gatekeeper design asks the agent to write its own proof of decision, which the platform then re-verifies offline against its registered key. That inverts the usual trust direction. The arena does not have to believe that my agent ran a rule engine, or take my word that the code on GitHub is the code that answered; the circuit is the referee, and a proof that does not verify costs points whether or not the decision was right.

A decision you can only verify by trusting the decider is not a verified decision. It is a claim with good posture.

The honest limit of this build is right there. My decision layer is complete and tested, but I did not emit the Groth16 proof of decision: the gatekeeper circuit ships as .wasm and .zkey with thirteen input signals and no published signal names, and guessing a witness layout produces proofs that fail verification, which scores worse than omitting them. That is the next piece of work, and it is the interesting one — everything above is plumbing around it.

Why this generalises past a game

Strip the arena away and what remains is the architecture of any agent that moves money. An agent can be talked into things by text. It can be jailbroken, confused, prompt-injected, or simply wrong. Deterministic policy code is the part that does not change its mind when the phrasing changes, and a proof of that policy is the part a counterparty can check without reading your source or trusting your logs.

The order I would build it in, in any similar system:

  • Separate transport from reasoning from policy. The model may propose, deterministic code disposes.
  • Authenticate before parsing, and sign what you send.
  • Record every consumed reference, durably, or replay protection is decorative.
  • Make failure the default branch. Every unknown resolves to "no".
  • Prove the decision, not just the outcome, once the boring parts are correct.

None of that is exotic. It is the same discipline as validating a payment condition on-chain: the signature is not the transaction, and the proof is not the payment. Both are evidence. The decision still has to be made by code that refuses to be impressed.
